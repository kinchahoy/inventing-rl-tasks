# Parallelize SymPy's symbolic state-space subsystem

Improve SymPy 1.14.0 so its symbolic state-space analysis uses available CPU cores efficiently on free-threaded CPython. The high-level anchor is `StateSpace.dsolve`. The scope includes the substantial public matrix and solver operations used by this subsystem. Make coordinated changes to the actual library; algorithms, internal representations, and helper functions may change. You have 60 minutes. `pytest` is installed for your own testing; it is not available to the submitted package.

Discover the optimization targets yourself through profiling and source inspection. Performance is assessed at the end-to-end interface and at a small number of constituent public operations chosen by the task authors; which ones, and the workloads, are not disclosed.

Preserve the complete supported public API and exact observable behavior, including accepted inputs, return types, symbolic and numeric results, ordering, mutations, and exception types and messages. The package must remain a drop-in replacement on ordinary GIL-enabled CPython too. Existing calls must benefit without new arguments, opt-in wrappers, or a caller-managed concurrency interface. Correctness is checked by exact comparison with the original on hidden cases across the subsystem's public API, on both runtimes and all core counts; the cases cover only a sample of the API, so do not rely on any particular call being unchecked.

For each assessed timed operation, let `T_original` be its original one-core GIL-enabled runtime, `T_1` your one-core free-threaded runtime, and `T_N` your free-threaded runtime with N available cores. Requirements are:

- Every timed input takes at least about 100 ms with the original library on one core (GIL build).
- `T_1 <= 1.05 * T_original`.
- Each doubling of cores must be faster: `T_1 / T_2` and `T_2 / T_4` at least 1.10 at the end-to-end interface, and at least 1.05 for each assessed constituent operation.

The verifier evaluates N = 1, 2, and 4 by restricting CPU affinity to that many distinct physical cores; adapt to the process's available CPU affinity. Each assessed operation is timed on three different inputs of the same kind (same sizes, different values), each in a fresh process, with the first call included and timing covering the call and the production of its complete result; the fixed cost of encoding a correct result, measured on the original library, is subtracted. Ratios are computed per input and their median is used. Each requirement applies to each assessed operation separately. Improvements must occur within individual calls; batching unrelated requests is insufficient. Required preparation, conversion, and result assembly count as computation. Do not move input-dependent work into excluded setup or deliberately slow one-core execution.

Runtime dependencies are limited to the supplied SymPy source, mpmath 1.3.0, and CPython's standard library. Do not install, add, vendor, bundle, or require additional third-party packages, or change the pinned dependency versions. You may add your own Python helper modules within the submitted package. The full ordinary standard library, including C-backed builtins and thread coordination, is allowed. No native extensions, custom compiled kernels, JITs, multiprocessing, subprocess computation, or external services. Process creation, sockets, and CPU-affinity changes are blocked in the verifier. Preserve the verifier-controlled runtime mode and CPU allocation. Do not specialize to benchmark inputs or detect verifier execution.

Edit `/app/sympy`; that complete package is submitted. Other filesystem changes are not submitted; the verifier supplies mpmath 1.3.0 unchanged. The untouched package is in `/opt/reference`. Matched CPython 3.15.2 builds are available as `python-gil` and `python-ft`. `/app/public_check.py` checks only runtime/package availability and contains no evaluation cases. Correctness and performance are assessed privately at both the high-level and constituent-operation interfaces.
